# Code Generation

## Overview

Code generation is the right answer when you have repetitive boilerplate that must stay in sync with a schema or specification. Generated code eliminates copy-paste errors, keeps clients and servers consistent with their API specs, and frees developers from writing mechanical code. The tradeoff: generated code is hard to debug, can be verbose, and requires discipline to keep the generation step in the build pipeline. This skill covers when to generate, how to generate well, and how to keep generated code from becoming a liability.

## When Codegen Is the Right Answer

**Do generate when:**
- You have a schema (OpenAPI, Protobuf, GraphQL) and need typed clients/servers from it
- You have repetitive boilerplate that follows a predictable pattern (CRUD operations, serialization)
- The source of truth is a spec file, and code must stay in sync with it
- You need consistent patterns across many similar entities (e.g., 50 message types)

**Don't generate when:**
- You only have 2-3 instances — just write them by hand
- The "schema" is just a list of names with no structure — a simple loop in a shell script suffices
- The generated code needs significant manual customization — you'll fight the generator forever
- You're generating code that's simpler to write directly (don't generate a 5-line function)

## Schema-Driven Generation

### OpenAPI → Client/Server Stubs

- **OpenAPI Generator** (`openapi-generator-cli`): Generates clients in 40+ languages, server stubs in many
- Generate only what you need: `--generate-models-only` if you just want types
- Customize with templates: override specific templates without forking the whole generator
- Validate the spec first: `openapi-generator-cli validate -i spec.yaml`

### Protobuf → Typed Messages

- `protoc` compiler with language plugins generates message classes and serialization
- Always use the latest `protoc` — older versions generate different code
- Generated code is not manually edited — changes go in `.proto` files
- Backward compatibility: never remove or rename a field, only add new ones

### GraphQL → Types

- `graphql-codegen`: Generates TypeScript types from GraphQL schemas and operations
- Generate from operations (queries/mutations), not just the schema — gives you typed results
- Plugin system: add custom visitors for project-specific patterns

## Template-Based Generation

### Text Templates

Simple and effective for most cases. Use your language's template engine:

- **JavaScript/TypeScript**: EJS, Handlebars, Pug
- **Python**: Jinja2, Mako
- **Go**: `text/template` (built-in)
- **Rust**: Tera, Askama (compile-time templates)

**Pattern**: Template file + data model → generated file

```python
# Jinja2 example
template = env.get_template('model.py.j2')
output = template.render(name="User", fields=[{"name": "id", "type": "int"}])
```

### When to Use AST-Based Generation

- You need to **modify** existing code, not create new files (codemods, migrations)
- You need to ensure the output is syntactically valid
- You need to preserve formatting, comments, and import ordering

Tools: Babel (JS), lib2to3/AST (Python), syn (Rust), go/ast (Go)

**Tradeoff**: AST manipulation is more complex to write but produces more reliable output. Use templates for new files, AST for modifications.

## Output Hygiene

### Mark Generated Files Clearly

Every generated file should have a header that says "don't edit this":

```python
# Generated by tools/gen_models.py — DO NOT EDIT
# Re-generate with: make generate
```

### Don't Manually Edit Generated Code

- If you need to customize, extend the generated class, don't modify it
- Use partial classes (C#), extension files, or wrapper functions
- If you must edit, the next generation step will overwrite your changes

### Determinism

Same input must always produce same output:

- **No timestamps** in generated code (they change every run)
- **No random IDs** — use deterministic naming from the schema
- **Sorted output** — sort fields, imports, and methods alphabetically or by schema order
- **No filesystem-order dependencies** — `os.listdir()` order varies by OS

## Running Codegen in CI

Generated code must stay in sync. If someone changes the schema without regenerating, the build should fail:

```yaml
# GitHub Actions pattern
- name: Generate code
  run: make generate
- name: Check for uncommitted changes
  run: |
    git diff --exit-code
    # Fails if generated code is out of date
```

This pattern ensures:
1. Schema changes always include updated generated code
2. No one accidentally runs with stale generated code
3. PR reviewers can see the generated output alongside the schema change

## Testing Generators

**Test the output, not the generator internals.**

```python
# Good: test what the generator produces
def test_generates_model_class():
    result = generate_model(schema={"name": "User", "fields": [...]})
    assert "class User:" in result
    assert "def __init__" in result

# Bad: test internal functions nobody cares about
def test_template_engine_renders():
    assert render("{{ name }}", {"name": "X"}) == "X"  # Testing the library, not your code
```

### Test Categories

1. **Golden file tests**: Generate output, compare to committed "golden" file. Update golden when you intentionally change output.
2. **Compilation tests**: Generate code, then compile/run it. If it doesn't compile, the generator is broken.
3. **Round-trip tests**: Generate → compile → run → verify output matches expected behavior.
4. **Schema coverage**: Ensure every field in the schema appears in the generated code.

## Common Pitfalls

- **Generating too much**: Only generate what you need. A 10,000-line client from a huge API spec is worse than targeted generation of the 5 endpoints you use.
- **Not versioning the generator**: Pin the generator tool version. Upgrading the generator can change output without schema changes.
- **Ignoring formatting**: Run the generated code through your formatter (prettier, black, gofmt) after generation.
- **Complex templates**: If your template has more logic than the code it generates, simplify the template or use a different approach.
- **Not committing generated code**: Some teams `.gitignore` generated files. This works for CI but makes local development harder. Commit generated code for discoverability, but enforce CI checks to keep it in sync.

## Windows-Specific Code Generation Notes

### Line Endings in Generated Code
Generated code should use consistent line endings regardless of the platform it runs on:

```python
# Always generate with LF line endings, even on Windows
def generate_file(content: str, path: str):
    # Normalize line endings to LF
    content = content.replace("\r\n", "\n")
    with open(path, "w", newline="\n") as f:
        f.write(content)
```

### Path Handling in Generators
```python
import os
from pathlib import Path

def generate_output_path(base_dir: str, filename: str) -> str:
    """Generate a cross-platform output path."""
    # pathlib handles Windows path separators automatically
    return str(Path(base_dir) / filename)

# Windows: C:\project\output\file.ts
# Unix: /project/output/file.ts
```

### PowerShell Script Generation
When generating PowerShell scripts from templates:
- Use UTF-8 BOM encoding for PowerShell compatibility
- Escape backticks (`` ` ``) in generated strings
- Use forward slashes in paths when possible (PowerShell accepts both)

```python
# Generate PowerShell-compatible script
def generate_ps_script(commands: list[str]) -> str:
    lines = ["#!/usr/bin/env pwsh", ""]
    for cmd in commands:
        lines.append(cmd)
    return "\n".join(lines)
```

## Checklist

- [ ] Codegen is the right tool (repetitive, schema-driven, not just 2-3 instances)
- [ ] Generated files are clearly marked as generated
- [ ] Generation is deterministic (no timestamps, random IDs, or filesystem-order deps)
- [ ] CI checks that generated code is up to date
- [ ] Generated code is not manually edited - customization via extension
- [ ] Generator is version-pinned (tool + templates)
- [ ] Output is formatted with the project's standard formatter
- [ ] Tests verify generated output, not generator internals
- [ ] Generated code uses LF line endings (even on Windows)
- [ ] Generated paths are cross-platform compatible
